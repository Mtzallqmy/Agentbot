# وثيقة متطلبات المنتج — منصة الوكيل والذكاء الاصطناعي

## 1. الهدف

منصة عربية أولاً تجمع في منتج واحد:

- دردشة متعددة مزودي الذكاء الاصطناعي عبر الويب وTelegram.
- وكيل برمجي ينفذ داخل Sandbox بصلاحيات وموافقات صريحة.
- تنزيل ومعالجة وسائط يملك المستخدم حق التعامل معها.
- لوحة إدارة مبنية على بيانات التشغيل الفعلية.
- نشر محايد للسحابة عبر حاويات Docker.

المعماريّة المستهدفة هي **Modular Monolith** بواجهة API وعمّال مستقلين، وليست مجموعة Microservices مبكرة.

## 2. المستخدمون والأدوار

| الدور | الصلاحيات الأساسية |
|---|---|
| `user` | الدردشة، الوسائط، المشاريع والتكاملات الخاصة به |
| `premium` | حصص أعلى وخصائص مفعلة وفق Feature Flags |
| `moderator` | مراجعة المهام والمحتوى دون الوصول إلى الأسرار |
| `admin` | إدارة المستخدمين والحصص والمهام والإعدادات التشغيلية |
| `superadmin` | إدارة الأدوار والسياسات والعمليات الأمنية الحساسة |

كل مورد يملك `owner_user_id` أو نطاق مشروع واضح. المنع هو الوضع الافتراضي.

## 3. نطاق MVP

### مشمول

1. تسجيل مستخدم Telegram وتوثيق جلسة ويب قصيرة العمر.
2. RBAC أساسي وعزل موارد المستخدم.
3. حفظ بيانات اعتماد مزود OpenAI-compatible مشفرة، اختبار الاتصال، جلب النماذج أو إضافتها يدوياً.
4. محادثات محفوظة مع بث تدريجي، إيقاف التوليد، أرشفة، وإعادة توليد.
5. Webhook آمن لـTelegram، قائمة عربية، ومنع التكرار بواسطة `update_id`.
6. تحليل رابط مدعوم عبر `yt-dlp`، تنزيل/تحويل/قص ملف عبر `FFmpeg` في Worker، تقدم وإلغاء وتنظيف مؤقت.
7. مشروع Agent محلي، أدوات ملفات وGit مقيدة، تشغيل اختبارات، وخط موافقة قبل العمليات الخارجية.
8. GitHub OAuth/App: ربط الحساب، allowlist للمستودعات، branch/commit/PR بعد موافقة.
9. لوحة ويب فعلية للمحادثات والمهام والمزودات، ولوحة إدارة لمقاييس من قاعدة البيانات والطابور.
10. PostgreSQL وRedis وS3-compatible storage، سجلات JSON، Health/Readiness، Docker Compose واختبارات أساسية.

### مؤجل بعد MVP

- Adapters أصلية لكل مزودي AI غير المتوافقين مع OpenAI.
- Kubernetes manifests متقدمة وautoscaling متعدد المناطق.
- تنفيذ إنتاجي على قواعد MySQL/MongoDB الخارجية؛ يبدأ MVP بـintrospection وقراءة PostgreSQL.
- ذاكرة دلالية طويلة المدى وRAG كامل.
- تنفيذ متوازٍ لوكلاء متعددين؛ MVP يستخدم Orchestrator حتمي بأدوار منطقية.
- توليد صور/صوت أصلي إلا عبر Adapter يعلن القدرة صراحة.

لا تظهر خاصية في الواجهة قبل وجود endpoint واختبار مسار نجاح وفشل لها.

## 4. قصص المستخدم ومعايير القبول

| القصة | معيار القبول |
|---|---|
| أضيف مزود AI | المفتاح مشفر، لا يعاد عرضه، والاختبار يعيد نتيجة منقحة |
| أبدأ محادثة | تحفظ الرسائل ويصل النص تدريجياً عبر SSE ويمكن الإلغاء |
| أرسل أمراً للبوت | يتحقق Secret Token ويُعالج `update_id` مرة واحدة |
| أنزل وسائط | تظهر الصيغ الفعلية، ينفذ Worker، ويصدر رابط مؤقت أو ملف Telegram |
| أشغّل الوكيل | كل خطوة وأداة وصلاحية ونتيجة مسجلة وقابلة للاستكمال |
| أدفع تغييرات GitHub | يعرض diff والأوامر ويطلب موافقة قبل push/PR |
| أدير النظام | تعرض اللوحة مقاييس مجمعة من البيانات الحقيقية |

## 5. المتطلبات غير الوظيفية

- **الأمن:** تشفير أسرار التطبيق، HTTPS في الإنتاج، SSRF guard، rate limits، redaction، وموافقات.
- **الاعتمادية:** مهام دائمة في PostgreSQL، ARQ فوق Redis، idempotency، retry/backoff وdead-letter.
- **الأداء:** p95 لطلبات API العادية أقل من 500ms دون زمن المزود؛ استجابة Webhook أقل من ثانيتين.
- **القابلية للنقل:** لا افتراض لخدمة سحابية بعينها؛ كل خدمة خارجية خلف Interface/Adapter.
- **المراقبة:** request/correlation IDs، Prometheus، OpenTelemetry اختياري، وSentry اختياري.
- **العربية:** RTL من البداية ونصوص قابلة للنقل لاحقاً إلى i18n.

## 6. مؤشرات النجاح

- نجاح Webhook دون تكرار ≥ 99.9%.
- نجاح استكمال المهام القابلة لإعادة المحاولة ≥ 95%.
- صفر أسرار خام في قاعدة البيانات أو السجلات.
- نجاح المسارات الحرجة في CI: auth، provider، streaming، webhook، approval، media.
- زمن استعادة Worker بعد إعادة التشغيل أقل من دقيقة للمهام المؤهلة.

## 7. خارج النطاق والسياسة

- لا تجاوز DRM أو paywalls أو الوصول إلى محتوى خاص.
- لا تشغيل أوامر عشوائية على مضيف الإنتاج.
- لا نشر أو push أو تكلفة خارجية دون اعتماد صالح وموافقة المستخدم.
- لا ضمان لدعم موقع أو نموذج إلا إذا أثبت Adapter الاختبار والقدرات.
